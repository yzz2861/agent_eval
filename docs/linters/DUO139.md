# DUO139

This linter tracks the identity of temporary file paths created by the
`tempfile` module. A path obtained from `NamedTemporaryFile.name` (or the
equivalent `TemporaryFile`, `SpooledTemporaryFile`, `TemporaryDirectory`,
`mkstemp`, and `mkdtemp` APIs) is only known to refer to the created
temporary file while that object still owns the path.

The analysis is intentionally limited to a single module. It follows direct
object aliases, path aliases, and a small, explainable subset of same-module
helper functions. Unknown calls are treated as analysis boundaries rather
than being assumed safe.

## Problematic code

Using the name after the object has released the path:

```python
import tempfile

tmp = tempfile.NamedTemporaryFile()
tmp.close()
process(tmp.name)
```

The same issue occurs when a context manager exits:

```python
import tempfile

with tempfile.NamedTemporaryFile() as tmp:
    pass

process(tmp.name)
```

Reassigning the last reference, deleting the object, or handing the object
itself to an unknown function also ends the proven identity:

```python
import tempfile

tmp = tempfile.NamedTemporaryFile()
path = tmp.name
tmp = None
process(path)
```

## Correct code

Use the path while the temporary object still owns it:

```python
import tempfile

with tempfile.NamedTemporaryFile() as tmp:
    process(tmp.name)
```

Or explicitly let the file persist:

```python
import tempfile

tmp = tempfile.NamedTemporaryFile(delete=False)
path = tmp.name
tmp.close()
process(path)
```

`mkstemp` and `mkdtemp` also produce persistent paths, so their names remain
valid after closing the descriptor or removing the owning variable.

## Rationale

With the default `delete=True`, closing a temporary file or leaving its
`with` block may unlink the path. Code that keeps using `.name` can then
operate on a missing file, or on a different file that has since been created
at the same location. This is a time-of-check-to-time-of-use (TOCTOU) class
of defect.

When there is a later path-based use that cannot be proven safe, the result is
reported at the first source location where the identity constraint was lost:
the closing call, the `with` statement, the reassignment, or the object
ownership boundary. A single identity is reported at most once.

Passing a path string to a function that is not understood is recorded as an
analysis boundary, but the path string itself does not own the file. A later
explicit close, unlink, rename, or object handoff is therefore the location
that ends the proven identity.

## Exceptions

* A `delete=False` temporary file retains its path after `close()` and after
  its context manager exits.
* `mkstemp` and `mkdtemp` return a path that is owned by the caller and is not
  removed automatically.
* Known read-only path consumers such as `open`, `os.stat`, `os.path.*`,
  `shutil.copy*`, and `print` do not end the path identity.
* Ownership transfers to same-module helpers are followed only when the
  helper is a straight-line function whose effect is unambiguous (for example
  `def cleanup(tmp): tmp.close()`). Other helpers are analysis boundaries.
