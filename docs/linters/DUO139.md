# DUO139

This linter searches for time-of-check to time-of-use (TOCTOU) race conditions
on filesystem paths. It builds a per-function file event graph that spans
branches, exception handlers and loops, then relates filesystem checks
(`os.path.exists`, `os.stat`, `os.access` and friends) to later uses of the
same path string (`open`, `os.open`, `os.rename`, `os.unlink` and friends).

## Why this matters

A path string is re-resolved every time it is used. When code checks a path
and later re-opens that same path, an attacker can replace the path target
(for example with a symlink) in the window between the check and the use.

Using an already-open file descriptor is different: descriptor operations do
not re-resolve any path, so replacing the path after the descriptor is opened
cannot redirect them.

## Problematic code

```python
import os


def read_config(path):
    if os.path.exists(path):
        with open(path) as config_file:
            return config_file.read()
```

Between `os.path.exists` and `open`, `path` could be swapped for a symlink to
a sensitive file.

## Correct code

Open the descriptor once with flags that make the operation atomic or that
refuse symlinks, then operate on the descriptor.

```python
import os


def read_config(path):
    descriptor = os.open(path, os.O_RDONLY | os.O_NOFOLLOW)
    with os.fdopen(descriptor) as config_file:
        return config_file.read()
```

For exclusive creation, combine `O_CREAT` with `O_EXCL` so the existence
check and creation are a single atomic operation:

```python
import os


def create_once(path):
    descriptor = os.open(
        path,
        os.O_WRONLY | os.O_CREAT | os.O_EXCL,
        0o600,
    )
    return descriptor
```

## Semantics modeled

* `os.open` with `O_EXCL` or `O_NOFOLLOW`, or `no_follow=True`, is treated as
  safe because it either makes check-and-create atomic or refuses a symlinked
  final component.
* A `dir_fd`-anchored `os.open` is only treated as safe when the directory
  descriptor is a locally tracked, no-follow descriptor and the open itself
  pins the final component with `O_NOFOLLOW` or `O_EXCL`. An unknown
  `dir_fd` never suppresses the finding.
* `os.fdopen` transfers ownership of an existing descriptor; operations on the
  resulting object stay descriptor-based and are not flagged.
* Descriptor-only functions such as `os.fstat`, `os.fchmod` and `os.fsync` do
  not re-resolve a path and are not flagged.
* Calls through unrecognized wrapper functions are marked uncertain: they add
  an invalidation condition but never remove an otherwise reachable finding.

## Report contents

Each result identifies a reachable check/use pair and lists the conditions
under which the check may have become invalid before the use, for example an
intervening branch, an exception handler, a loop back edge, an intervening
filesystem mutation, a path-variable rebind, or an unknown wrapper.

## Exceptions

None. Races that cannot be ruled out statically are reported, with uncertainty
called out in the message rather than silently suppressed.
