# DUO139

This linter reviews temporary resource usage inside each local function. It
follows a caller-configured factory API and a caller-configured set of
security-check or release APIs, then reports exits that return while the
resource is still pending.

The analysis is intentionally source-only. Placeholder functions and
convention declarations in the analyzed file are read from the AST and are
never imported or executed.

Resources created by a configured factory inside the function and resource
parameters with an explicit resource annotation or an obvious resource name
(`resource`, `tmp_path`, `tempfile`, ...) are both followed.

## Problematic code

Both branches below appear to use the same cleanup call, but the first
branch returns before that call can run:

```python
def acquire_temp():
    ...

def security_check(resource):
    ...

def handle(flag):
    resource = acquire_temp()
    if flag:
        return resource
        security_check(resource)  # unreachable
    security_check(resource)
    return resource
```

The diagnostic is reported at the `return` that actually diverges, not at the
shared cleanup call or at the factory.

## Correct code

```python
def handle(flag):
    resource = acquire_temp()
    try:
        if flag:
            return resource
        return resource
    finally:
        security_check(resource)
```

The `finally` block is applied to every exit, including exception exits.

## Contracts

By default a configured check is treated as completing the check when it is
called. A check can instead be declared as a boolean predicate:

```python
class ProjectLinter(BadTemporaryResourceUseLinter):
    factories = ('project.acquire_temp',)
    checks = ('project.security_check', 'project.release_temp')
    contracts = {'project.security_check': 'bool'}
```

For a boolean check only the truthy branch is proof. A bare call to a
boolean check, or a call whose result is never consumed, is not proof.

## Conventions and placeholders

A same-file declaration or a decorated stub definition can mark a function as
a check without importing it:

```python
SECURITY_CHECKS = ('release_temp',)

def release_temp(resource):
    ...
```

Decorators such as `@security_check`, `@cleanup`, and `@dlint_check` on a
placeholder definition are also honoured.

## Unknown contracts

If a pending resource is passed to a call that is neither a configured check
nor a declared handoff, the path is reported as `contract_unknown`. This is a
review item, not a claim that the resource definitely leaked.

## Python API

The same evidence is available without Flake8:

```python
from dlint.flow import collect_evidence

for function in collect_evidence(source):
    for exit in function.exits:
        print(exit.kind, exit.status, exit.lineno, exit.path_text)
```

`normal`, `exception_cleanup`, `contract_unknown`, `unchecked`, and
`unchecked_exception` are the stable status names. The function-level result
also exposes `normal_returns`, `exception_cleanups`, `unknown_branches`, and
`problems`.

## Exceptions

Existing rules, including `DUO121` for `tempfile.mktemp`, keep their original
alert numbers and messages. `DUO139` only adds branch evidence; it does not
renumber or replace another rule.

By default, branch evidence for `tempfile.mktemp` keeps the original `DUO121`
number, while custom temporary-resource factories use `DUO139`. This can be
controlled explicitly:

```python
linter = BadTemporaryResourceUseLinter(preserve_original_code=True)
```

Set it to `False` to use `DUO139` for every factory. In all cases the existing
`DUO121` factory-call diagnostic is unchanged.
