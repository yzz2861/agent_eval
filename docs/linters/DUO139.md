# DUO139

This linter inspects dictionaries passed to `logging.config.dictConfig` and
lists the factory dotted paths Python will parse or call when the shared
logging configuration is applied. Only the single module containing the
`dictConfig` call is analyzed; the module is never imported or executed.

## Factory slots

Three locations cause Python to resolve a callable:

* `handlers.<name>["class"]` - handler classes are always instantiated
* `formatters.<name>["()"]` - custom formatter factories
* `filters.<name>["()"]` - custom filter factories

## What is analyzed

* Local dictionary literals
* Explicit merges via `**other` and `dict(base, **override)`; later sources
  override earlier ones, so findings land on the path that is actually
  enabled
* A bounded chain of plain-name constant references, including constants
  used for whole sections or individual handler/formatter/filter entries

Values that cannot be resolved statically (function calls, attribute
lookups, class objects, unknown names) are reported with an
`unresolved` status instead of being guessed at. Strings appearing in
ordinary description positions are ignored; only values found at a factory
slot enter the approval list.

## Problematic code

```python
import logging.config

logging.config.dictConfig({
    "version": 1,
    "handlers": {
        "console": {
            "class": "thirdparty.log.ColoredHandler",
        },
    },
})
```

## Correct code

Factories shipped with the standard library (`logging.Formatter` and
`logging.Filter`) are pre-approved and produce no findings. Reviewed
project or third-party factories can be declared through a subclass:

```python
import dlint


class DlintReviewedLoggingConfigLinter(
    dlint.linters.BadLoggingConfigUseLinter
):
    approved_factories = (
        dlint.linters.BadLoggingConfigUseLinter.approved_factories
        + ("thirdparty.log.ColoredHandler",)
    )
```

## Rationale

A shared logging configuration is loaded in every installation
environment. Any dotted path it names is imported and invoked during
configuration, so each non-standard factory must be reviewed before
release. The structured `factory_findings` report and deduplicated
`get_approval_list` output make that review explicit, while
`get_results` keeps the existing flake8 plugin output compatible.
