# DUO139

This linter detects a user-controlled file path reaching a file-reading sink
without first passing through the configured path validator. It is built on
Dlint reusable control flow analysis (dlint.flow), which reasons about
reachable paths rather than assuming that a syntactic check always executes.

## Problematic code

A bare if is not validation, and a validator whose exception is swallowed
does not protect the later sink:

    def read(name):
        if name:  # not a sanitizer
            open(name)

    def read(name):
        try:
            validate_path(name)
        except ValueError:
            pass  # exception swallowed: validation was bypassed
        open(name)

Reassigning the path inside finally also reopens the route to the sink,
because the finally body runs after the validator on every exit:

    def read(name):
        try:
            validate_path(name)
        finally:
            name = user_supplied_path()
        open(name)

## Correct code

Call the configured validator (a raising contract) on every path before the
sink, and let invalid inputs propagate instead of swallowing them:

    def read(name):
        validate_path(name)
        with open(name) as handle:
            return handle.read()

For a boolean-contract validator, only the accepting branch is considered
validated:

    def read(name):
        if is_path_ok(name):
            return open(name).read()
        raise ValueError("invalid path")

## Rationale

Treating the parameter passed a check as equivalent to the parameter being
safe is unsound whenever control flow can bypass the check. Early
return/raise, break/continue, loop else, swallowed exceptions and finally
reassignment all create reachable paths on which validation never happens.
This linter reports the shortest reachable branch sequence as evidence. When
the number of explored states exceeds the configured budget the result is
reported as unknown rather than silently treated as clean.
