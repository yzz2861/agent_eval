RFC 9068: JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens
==================================================================

.. module:: authlib.oauth2.rfc9068

This section contains the generic implementation of :rfc:`9068`.
JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens allows
developers to generate JWT access tokens.

Using JWT instead of plain text for access tokens result in different
possibilities:

- User information can be filled in the JWT claims, similar to the
  :ref:`specs/oidc` ``id_token``, possibly making the economy of
  requests to the ``userinfo_endpoint``.
- Resource servers do not *need* to reach the authorization server
  :ref:`specs/rfc7662` endpoint to verify each incoming tokens, as
  the JWT signature is a proof of its validity. This brings the economy
  of one network request at each resource access.
- Consequently, the authorization server do not need to store access
  tokens in a database. If a resource server does not implement this
  spec and still need to reach the authorization server introspection
  endpoint to check the token validation, then the authorization server
  can simply validate the JWT without requesting its database.
- If the authorization server do not store access tokens in a database,
  it won't have the possibility to revoke the tokens. The produced access
  tokens will be valid until the timestamp defined in its ``exp`` claim
  is reached.

This specification is just about **access** tokens. Other kinds of tokens
like refresh tokens are not covered.

:rfc:`9068` define a few optional JWT claims inspired from :rfc:`7643` that can
can be used to determine if the token bearer is authorized to access a
resource: ``groups``, ``roles`` and ``entitlements``.

This module brings tools to:

- generate JWT access tokens with :class:`~authlib.oauth2.rfc9068.JWTBearerTokenGenerator`
- protected resources endpoints and validate JWT access tokens with :class:`~authlib.oauth2.rfc9068.JWTBearerTokenValidator`
- introspect JWT access tokens with :class:`~authlib.oauth2.rfc9068.JWTIntrospectionEndpoint`
- deny JWT access tokens revokation attempts with :class:`~authlib.oauth2.rfc9068.JWTRevocationEndpoint`

Audience
--------

Per :rfc:`RFC 9068 §2.2 <9068#section-2.2>`, the ``aud`` claim holds the identifier of the
resource that receives the token. Per :rfc:`RFC 9068 §3 <9068#section-3>`, the authorization
server uses a default resource when the request has no ``resource`` parameter.
Return it from
:meth:`~authlib.oauth2.rfc9068.JWTBearerTokenGenerator.get_audiences`:

.. code-block:: python

    class MyJWTBearerTokenGenerator(JWTBearerTokenGenerator):
        def get_audiences(self, client, user, scope):
            return "https://api.example.org"

The method can also choose the resources from the client, the user or the
scope. The resource server gives the same identifier to
:class:`~authlib.oauth2.rfc9068.JWTBearerTokenValidator` as
``resource_server``.

Token validation
----------------

Per :rfc:`RFC 9068 §4 <9068#section-4>`,
:class:`~authlib.oauth2.rfc9068.JWTBearerTokenValidator` validates incoming
JWT access tokens in five layers:

1. **Signature trust**: the token is verified with the keys returned by
   :meth:`~authlib.oauth2.rfc9068.JWTBearerTokenValidator.get_jwks`. A token
   that carries a ``jku`` or ``jwk`` header is always rejected: the key never
   comes from the token itself.
2. **Issuer binding**: the ``iss`` claim must match the issuer whose key
   verified the signature.
3. **Type and purpose**: the ``typ`` header must be ``at+jwt`` (or
   ``application/at+jwt`` in the default, backward-compatible profile).
4. **Claim structure**: ``iss``, ``sub``, ``client_id``, ``aud``, ``exp``,
   ``iat`` and ``jti`` must be present with the JSON type required by
   :rfc:`RFC 9068 §2.2 <9068#section-2.2>`. A missing claim and a claim with
   the wrong type raise distinct errors that carry the claim name, so audits
   can tell them apart.
5. **Resource audience**: the ``aud`` claim must contain the configured
   ``resource_server``.

Every failure becomes the generic RFC 6750 ``invalid_token`` error for the
client. The internal logs only contain the error kind and the claim name; the
raw JWT and identifying claims such as ``jti`` are never logged.

Strict profile
~~~~~~~~~~~~~~

The default profile keeps accepting tokens already in production. Pass
``strict=True`` to enable the stricter rules of :rfc:`RFC 9068 §2.1
<9068#section-2.1>` and :rfc:`RFC 8693 §4.2 <8693#section-4.2>`:

- the ``typ`` header must be the canonical ``at+jwt`` value;
- the ``scope`` claim, when present, must be a space-separated string rather
  than a JSON array.

.. code-block:: python

    validator = MyJWTBearerTokenValidator(
        issuer="https://authorization-server.example.org",
        resource_server="https://resource-server.example.org",
        strict=True,
    )

Several issuers
~~~~~~~~~~~~~~~

A resource server can accept tokens from several issuers by passing a mapping
as the ``issuer`` argument. Each value binds an issuer to its JWK set and,
optionally, its own resource server identifier:

.. code-block:: python

    validator = JWTBearerTokenValidator(
        issuer={
            "https://as-a.example.org": {
                "jwks": jwks_a,
                "resource_server": "https://api.example.org",
            },
            "https://as-b.example.org": {
                "jwks": jwks_b,
                "resource_server": "https://api.example.org",
            },
        }
    )

The unverified ``iss`` claim is only used to select the issuer-bound key; it
is checked again once the signature is verified. You can also omit the
``jwks`` keys and re-implement ``get_jwks(issuer)`` to load the key set of
the selected issuer dynamically.

UserInfo endpoint
-----------------

The :ref:`specs/oidc` :class:`~authlib.oidc.core.UserInfoEndpoint` is a
protected resource (OpenID Connect Core 1.0 §5.3). It accepts JWT access tokens if
you protect it with a :class:`~authlib.oauth2.rfc9068.JWTBearerTokenValidator`.

Per :rfc:`RFC 9068 §4 <9068#section-4>`, the validator checks that the ``aud`` claim contains
the identifier of the resource server. Use the URL of the userinfo endpoint as
this identifier:

.. code-block:: python

    USERINFO_URL = "https://authorization-server.example.org/oauth/userinfo"

    class MyJWTBearerTokenValidator(JWTBearerTokenValidator):
        def get_jwks(self): ...

    resource_protector = ResourceProtector()
    resource_protector.register_token_validator(
        MyJWTBearerTokenValidator(
            issuer="https://authorization-server.example.org",
            resource_server=USERINFO_URL,
        )
    )

The token generator must then add this URL to the audience of the tokens that
are issued for a user with the ``openid`` scope. ``API_URL`` is the identifier
of your other resource server:

.. code-block:: python

    class MyJWTBearerTokenGenerator(JWTBearerTokenGenerator):
        def get_audiences(self, client, user, scope):
            audiences = [API_URL]
            if user and "openid" in (scope_to_list(scope) or []):
                audiences.append(USERINFO_URL)
            return audiences

Tokens without a user, such as client credentials tokens, have the client ID
in their ``sub`` claim. They must not reach the userinfo endpoint. Per
:rfc:`RFC 9068 §5 <9068#section-5>`, if a client ID can be equal to a user ID, do not let
clients choose their client ID.

A JWT access token only carries identifiers. Override
:meth:`~authlib.oidc.core.UserInfoEndpoint.get_token_client` and
:meth:`~authlib.oidc.core.UserInfoEndpoint.get_token_user` to load the client
and the user:

.. code-block:: python

    class UserInfoEndpoint(oidc.core.UserInfoEndpoint):
        def get_token_client(self, token):
            return self.server.query_client(token["client_id"])

        def get_token_user(self, token):
            return User.get(token["sub"])

        ...

    server.register_endpoint(UserInfoEndpoint(resource_protector=resource_protector))
