# Test Adapter

The built-in Faraday Test adapter lets you define stubbed HTTP requests. This can
be used to mock out network services in an application's unit tests.

The easiest way to do this is to create the stubbed requests when initializing
a `Faraday::Connection`. Stubbing a request by path yields a block with a
`Faraday::Env` object. The stub block expects an Array return value with three
values: an Integer HTTP status code, a Hash of key/value headers, and a
response body.

```ruby
conn = Faraday.new do |builder|
  builder.adapter :test do |stub|
    # block returns an array with 3 items:
    # - Integer response status
    # - Hash HTTP headers
    # - String response body
    stub.get('/ebi') do |env|
      [
        200,
        { 'Content-Type': 'text/plain', },
        'shrimp'
      ]
    end

    # test exceptions too
    stub.get('/boom') do
      raise Faraday::ConnectionFailed
    end
  end
end
```

You can define the stubbed requests outside of the test adapter block:

```ruby
stubs = Faraday::Adapter::Test::Stubs.new do |stub|
  stub.get('/tamago') { |env| [200, {}, 'egg'] }
end
```

This Stubs instance can be passed to a new Connection:

```ruby
conn = Faraday.new do |builder|
  builder.adapter :test, stubs do |stub|
    stub.get('/ebi') { |env| [ 200, {}, 'shrimp' ]}
  end
end
```

It's also possible to stub additional requests after the connection has been
initialized. This is useful for testing.

```ruby
stubs.get('/uni') { |env| [ 200, {}, 'urchin' ]}
```

You can also stub the request body with a string or a proc.
It would be useful to pass a proc if it's OK only to check the parts of the request body are passed.

```ruby
stubs.post('/kohada', 'where=sea&temperature=24') { |env| [ 200, {}, 'spotted gizzard shad' ]}
stubs.post('/anago', -> (request_body) { JSON.parse(request_body).slice('name') == { 'name' => 'Wakamoto' } }) { |env| [200, {}, 'conger eel'] }
```

If you want to stub requests that exactly match a path, parameters, and headers,
`strict_mode` would be useful.

```ruby
stubs = Faraday::Adapter::Test::Stubs.new(strict_mode: true) do |stub|
  stub.get('/ikura?nori=true', 'X-Soy-Sauce' => '5ml' ) { |env| [200, {}, 'ikura gunkan maki'] }
end
```

This stub expects the connection will be called like this:

```ruby
conn.get('/ikura', { nori: 'true' }, { 'X-Soy-Sauce' => '5ml' } )
```

If there are other parameters or headers included, the Faraday Test adapter
will raise `Faraday::Test::Stubs::NotFound`. It also raises the error
if the specified parameters (`nori`) or headers (`X-Soy-Sauce`) are omitted.

You can also enable `strict_mode` after initializing the connection.
In this case, all requests, including ones that have been already stubbed,
will be handled in a strict way.

```ruby
stubs.strict_mode = true
```

## Stateful stubs

When an API has a required sequence, organize stubs into named states. A stub
marked with `transition:` consumes a one-time transition and changes the current
state. Other stubs in the state can be called repeatedly without changing it.

The request block receives the usual `Faraday::Env`, followed by a context. Use
the context to store values generated by one request and read them in a later
state. The same URL may therefore return a different response depending on the
current state.

```ruby
stubs = Faraday::Adapter::Test::Stubs.new do |stub|
  stub.state :draft do |state|
    state.post '/documents', transition: :submitted do |env, context|
      document = JSON.parse(env.body)
      context[:document_id] = document.fetch('id')
      [201, {}, 'draft created']
    end

    state.get '/documents' do
      [409, {}, 'submit the draft first']
    end
  end

  stub.state :submitted do |state|
    state.post '/documents', transition: :ready do |_env, context|
      context[:result] = "result-#{context[:document_id]}"
      [202, {}, 'submitted']
    end

    state.get '/documents' do
      [409, {}, 'result is not ready']
    end
  end

  stub.state :ready do |state|
    state.get '/documents' do |_env, context|
      [200, {}, context[:result]]
    end
  end
end

conn.post('/documents', JSON.dump(id: 42)) # 201, state: :draft -> :submitted
conn.post('/documents')                    # 202, state: :submitted -> :ready
conn.get('/documents')                     # 200, body: "result-42"
```

For conditional transitions, pass `transition: true` and choose the target in
the response block with `context.transition_to`:

```ruby
state.post '/documents', transition: true do |env, context|
  payload = JSON.parse(env.body)
  context.transition_to(payload.fetch('ready') ? :ready : :submitted)
  [202, {}, 'accepted']
end
```

The first state defined is used as the initial state. Pass `initial: true` to a
later state definition to select it explicitly, or call `initial_state=` before
making requests.

Making a request that only exists in another state raises
`Faraday::Adapter::Test::Stubs::InvalidStateTransition`. The error names the
current state and the state in which the request is available. If the request is
not stubbed in any state, the usual `Stubs::NotFound` error is raised instead.

A transition is claimed before its response block runs. If two concurrent
requests match the same one-time transition, one gets the transition and the
other raises `Stubs::TransitionInProgress`. If the losing request is processed
after the winner has already committed, it raises `Stubs::TransitionConsumed`
instead. Both inherit from `Stubs::InvalidStateTransition`. If the winning response block
raises, the claim is released so the request can be retried.

Regular stubs created directly with `stubs.get`, `stubs.post`, and similar
methods remain independent, repeatable according to the existing one-shot
matching rules, and do not inspect or change the current state.

Finally, you can treat your stubs as mocks by verifying that all of the stubbed
calls were made. NOTE: this feature is still fairly experimental. It will not
verify the order or count of any stub.

```ruby
stubs.verify_stubbed_calls
```

After the test case is completed (possibly in an `after` hook), you should reset
the stubs so each test starts with its own set. When you hold a reference to the
`Stubs` instance, call `clear` to remove every stub, including consumed ones.

```ruby
stubs.clear
```

Alternatively, if you rely on the default connection, you can clear it to prevent
it from being cached between different tests.

```ruby
Faraday.default_connection = nil
```
